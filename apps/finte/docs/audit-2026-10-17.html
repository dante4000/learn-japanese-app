Revision: ab62017e367094d476830d625031c391852fdf71 Result: 14 findings: 2 high priority, 10 medium priority, 2 low priority. No production changes made.

The main risks are loss of history during reconnection and financial values that hide missing data. The test suite passes, but it does not cover these cases. Fix data safety and completeness before further visual polish.

Scope and evidence

Reviewed financial calculations, income classification, refunds, rent estimates, account availability, recurring bills, card calculations, CSV import/export, sync, encrypted storage, authentication, API validation, tables, charts, detail panels, loading states, and mutation feedback. Reviewed the app source, README, existing specifications, and tests.

Evidence labels below distinguish executed fixture checks from source tracing. Fixtures used invented data. No bank connection was removed, no live data was edited, and no new bank sync was triggered.

Live visual coverage is incomplete. This prevented a reliable current desktop/mobile, contrast, focus, clipping, and animation review. P1 — High priority

F01. Reconnection requires deleting bank history

Evidence: source trace. ConnectionsList.tsx:74 tells users who need reauthentication to remove and re-link the bank. The delete route:28 deletes the stored bundle. createLinkToken:59 only creates new links; it has no existing-item update flow.

Impact: Routine authentication repair deletes stored transactions and edits. A new link cannot be relied on to restore older imported history or annotations.

Fix: Add a reconnect action that opens Plaid Link in update mode for the existing item. Preserve its bundle and cursor. Keep removal as a separate destructive action. Plaid documents this recovery flow for login-required and expiring connections: Plaid update mode.

Regression check: Repair an expired sandbox item. Verify unchanged account IDs, old transactions, CSV history, categories, notes, and hidden flags. Verify that cancellation preserves the connection.

F02. Missing balances look like zero debt or zero assets

Evidence: executed fixture and source trace. computeNetWorth:150 treats null balances as zero. Overview:82 also formats a focused account's null balance as $0. Sync deliberately clears balances when an account disappears from a successful account refresh.

Observed: An unavailable credit account with a last reported balance of $500 contributes $0 in liabilities. Its focused overview can show $0 with “balance owed.” There is no completeness flag in the net-worth result.

Impact: Missing access can look like debt repayment. Removing a reported liability can produce an apparent net-worth gain without a payment.

Fix: Show “Balance unavailable” for unknown balances. Label aggregate totals as partial and list excluded accounts. Keep last reported values with their date, separate from current balances. Do not infer zero from account closure or absence.

Regression check: Cover reported → unavailable → reported transitions for an asset and a liability. Verify totals, snapshots, the overview, and supporting details all expose incomplete coverage.

P2 — Medium priority

F03. Different currencies are added and labeled as one currency

Evidence: executed fixture and source trace. analytics.ts:153 selects the first account's currency and adds every balance. TransactionsView.tsx:196 passes a shared currency to each transaction row.

Observed: USD 100 plus EUR 100 produces net worth 200 USD, with no exchange conversion. This is conditional on mixed-currency data; it is not a claim that the current ledger contains EUR.

Fix: Group totals by currency, or apply explicit dated exchange rates. Format individual rows using their own currency. Apply the same rule to cash flow, charts, manual entries, and exports.

Regression check: Use two currencies and reverse account order. Values must not change their currency label or be combined without conversion.

F04. Full CSV export permits spreadsheet formulas

Evidence: executed harmless fixture and source trace. CSV export:10 only escapes CSV punctuation. A string =1+1 remains =1+1. Bank descriptions, merchants, and notes pass through this function. tableCsv:56 already protects text in table exports.

Impact: Spreadsheet software can interpret exported text as formulas. Exploitation depends on supplied text and spreadsheet behavior; no exploit was attempted. See OWASP CSV injection.

Fix: Share formula-safe text serialization across exports. Preserve actual numeric amount cells as numbers.

Regression check: Export harmless strings starting with formula characters, whitespace, tabs, quotes, commas, and newlines. Verify text remains text after parsing and numeric values retain their sign.

F05. The advertised CSV backup cannot restore the app's state

Evidence: executed fixture. Settings:52 calls the export a backup. csvToTransactions:222 imports all rows into one selected account and regenerates IDs. It ignores exported pending/hidden flags, notes, merchant values, and per-row currencies. Export also omits manual entries, baselines, card settings, and snapshots.

Observed: An exported-shaped EUR row with pending=true, hidden=true, and a note imports as USD, posted, visible, and without its note. It receives a new ID and account.

Impact: Reimport can change totals, reveal excluded rows, and lose account identity. The CSV remains useful for analysis, but it is not a restorable app backup.

Fix: Label the current file as a transaction export. Add a versioned backup/restore format with validation, preview, and explicit merge/replace behavior.

Regression check: Round-trip a multi-account state with edits, pending rows, hidden rows, manual entries, estimates, and card settings. Compare the restored state before committing it.

F06. Bilt Overview ignores closed and unavailable status

Evidence: executed fixtures. findBiltAccount:133 matches the account name without checking cardStatus or availability. Overview:54 consumes this result.

Observed: With bilt-mastercard marked closed and a $4,100 housing override, the meter still returns 250 projected points. An unavailable Bilt account also returns a meter. This is a separate gap from the Reserve status fix.

Fix: Use the same active-card eligibility rule in Overview and Cards. Keep historical spending accessible without current rewards prompts.

Regression check: Active, closed, unavailable, and unlinked Bilt states must agree across both pages. Include multiple matching historical accounts.

F07. A failed balance refresh still reports a healthy sync

Evidence: executed merge fixture and provider source trace. plaidSync:229 silently catches /accounts/get failures. buildBundle:87 always sets healthy status and advances the sync timestamp after a transaction sync.

Observed: An incomplete result with no accounts preserves an old balance while marking the item healthy and newly synced. Preserving the old data is correct; presenting it as refreshed is not.

Fix: Track transaction and balance freshness separately. Return a partial-success warning when current balances could not refresh. Keep account-absence detection gated on a successful complete response.

Regression check: Make transaction sync succeed and account refresh fail. Verify retained history, stale-balance labeling, and a useful retry state.

F08. Missing months disappear from charts and averages

Evidence: executed fixture. cashFlowByMonth:179 creates rows only for months present in transactions. windowMonths:19 takes the last months with spend/income activity. Analysis:74 labels that window as “last N months.”

Observed: $100 in August and $100 in October produce two rows and average spending of $100. September is absent. A twelve-row window can span more than twelve calendar months.

Fix: Show a continuous calendar axis for calendar periods. Distinguish known zero activity from unavailable history. State the actual date span and average denominator. If keeping an activity-month mode, name it explicitly.

Regression check: Cover a missing middle month, transfer-only month, pending-only month, and partial first/last months. Do not fill unknown bank coverage with invented zeroes.

F09. Selecting 1M can silently show all history

Evidence: mounted component fixture with Happy DOM. NetWorthArea:162 falls back to all snapshots when the selected range has fewer than two records, but retains the selected range label.

Observed: With January 1 and October 1 records, selecting 1M still includes both records and the $100 January-to-October change under “past month.”

Fix: Keep the selected range. Show its single point with an insufficient-history message, or use a clearly labeled boundary value where justified. Never silently widen the range.

Regression check: Click each range with zero, one, and two in-range records. Assert dates, headline change, table rows, and labels agree.

F10. Several successful saves can still look unsaved

Evidence: source trace; live propagation timing was not measured this pass. Storage uses a 60-second blob cache window. useSavedRefresh handles it with saved feedback and bounded refreshes. ManualEntries:51, BiltRentMeter:69, and CsvImport:86 only refresh once. Card status updates local state without refreshing server data.

Impact: A form can clear and its spinner can stop while the saved value is absent from the refreshed view. A retry can create a duplicate manual entry. Later navigation can briefly show old card status.

Fix: Apply one consistent saved/propagating/visible contract. Reuse the existing bounded refresh behavior, or make the mutation response update the relevant view immediately. Reserve error messages for failed writes.

Regression check: Return a successful save followed by stale reads. Verify the user sees saved feedback, eventual refresh, and no invitation to submit the same entry again.

F11. Failed Plaid revocation is hidden after removal

Evidence: source trace. The delete route:36 catches provider revocation failure and returns success without a warning. The confirmation says removal revokes access.

Impact: Local deletion can succeed while access remains authorized at Plaid. The user cannot distinguish those outcomes.

Fix: Preserve the local-delete result, but report the failed revocation and give a recovery path. Do not silently restore deleted credentials. Define a deliberate revocation retry strategy if needed.

Regression check: Mock a successful storage deletion and failed provider revoke. Assert an explicit warning and clear next action. Also cover successful revoke and storage conflict.

F12. Card credit corrections only persist in one browser

Evidence: source trace. CreditCardsView:230 reads overrides from mt.cardperks.v4 in localStorage. Writes stay in localStorage and storage errors are ignored.

Impact: Manual corrections affect captured credits and card value, but disappear on another device or after browser-data removal. A blocked storage write can look saved until reload.

Fix: Persist financial corrections in encrypted app metadata. If browser-only storage is intentional, label that limit and show write failures.

Regression check: Save a correction, start a fresh browser session, and verify the same result. Simulate a storage error and verify honest feedback.

P3 — Low priority

F13. Estimate management links to the wrong page

Evidence: source trace. details.ts:229 links “Manage estimates and import history” to Settings. The baseline editor is on Recurring; Settings only handles the import part.

Fix: Split this into “Manage estimates” → Recurring and “Import history” → Settings. Preserve useful context.

Regression check: Open an estimated rent detail and verify both destinations expose the named task.

F14. Security copy describes the wrong cookie policy

Evidence: source trace. Settings says the session cookie is SameSite-strict. auth.ts:38 uses lax to support bank OAuth returns.

Fix: Correct the copy. Do not switch to strict solely to match the text; that can break the documented OAuth return flow.

Regression check: Compare the claim with production cookie configuration and test the bank return flow.

Controls that passed review

  • Existing tests cover pending-to-posted edit carryover, sync account retention, category/income exclusions, refunds, rent-baseline dates, card status, card rewards/credits, encrypted storage conflicts, table behavior, and detail-panel interactions.
  • Detail-panel tests cover stale request races, retry, browser history, outside dismissal, and origin state. Native dialog semantics and close controls exist in source.
  • Chart tests cover signed refunds, null/empty values, keyboard controls, exact-value data tables, and six-month labels including September.
  • Loading feedback is delayed and dismissible. Detail loading has an error/retry state. Reduced-motion rules exist. These are source/test findings, not a completed visual accessibility certification.
  • The recent Bilt rent-gap explanation distinguishes estimates from posted charges. Account history survives a successful account refresh that omits an old account. The remaining gaps are F02, F06, and F07.
  • Protected read routes rejected unauthenticated access in the production checks. Encryption, conditional storage writes, and signed session checks are present. No authentication bypass was demonstrated.

Security and operational follow-up

These are hardening or verification tasks, separate from the 14 defects:

  • Resolve the five development dependency audit entries through a compatible dependency update. Re-run lint, tests, and build. Production dependency audit is currently clean.
  • Login throttling is process-local and explicitly best-effort in ratelimit.ts. A serverless deployment does not have a shared global attempt limit.
  • Sessions last 400 days. The authenticated session check does not consult the password hash or use loginAt for revocation. Document how to revoke all sessions; changing only the password hash does not invalidate existing cookies.
  • Review password hashing and recovery policy separately. The current comparison uses SHA-256. Do not treat a clean dependency scan as a complete security assessment.
  • Test a full encrypted-data restore in an isolated environment. Verify backups include metadata and connection history without exposing access tokens to the browser.
  • Verify all issuer benefits, fee dates, and reward rules against current primary sources before treating card estimates as issuer statements. This audit tested software behavior, not every catalog term.

Phase 2 — Consistent behavior: F06–F10 and F12. Align card eligibility, freshness, periods, saved feedback, and persistent corrections.
